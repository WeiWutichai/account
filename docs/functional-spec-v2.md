# AccountSystem — Functional Spec v2 (SaaS, Multi-company)

Nov 5, 2026 · @wei

v2 เปลี่ยนเป้าหมายจากระบบใช้ในองค์กรเดียว เป็น SaaS ที่หนึ่ง product รองรับหลายบริษัทแยกข้อมูลขาดจากกัน และปิดช่องว่างของ function ที่ v1 ยังขาด

## 1. ทิศทาง v2

AccountSystem v2 เป็นระบบบัญชี SaaS สำหรับธุรกิจไทย ขายให้ลูกค้าหลายราย โดยลูกค้าหนึ่งรายมีได้หลายบริษัท (หลายชุดบัญชี) และผู้ใช้หนึ่งคนเข้าได้หลายบริษัทด้วย login เดียว ข้อมูลของแต่ละบริษัทแยกขาดกันในระดับฐานข้อมูล ไม่ใช่แค่ filter ในโค้ด

| ประเด็น | v1 (4 พ.ย.) | v2 (5 พ.ย.) |
| --- | --- | --- |
| ผู้ใช้ปลายทาง | องค์กรของเราเอง | ลูกค้าภายนอกหลายราย (SaaS) + องค์กรเราเป็นลูกค้ารายแรก |
| การแยกข้อมูล | `company_id` + RLS ทุกตาราง | schema ต่อบริษัท + ตารางกลางสำหรับผู้ใช้/สิทธิ์/billing |
| บริษัทต่อบัญชีผู้ใช้ | 1 | ไม่จำกัด สลับได้ในหน้าจอเดียว |
| Onboarding | ตั้งค่าโดย dev | self-service: สมัคร → สร้างบริษัท → เลือกผังบัญชีตั้งต้น → ใช้งานได้ใน 5 นาที |
| แพ็กเกจ/การคิดเงิน | ไม่มี | plan + ขีดจำกัด (จำนวนบริษัท ผู้ใช้ เอกสาร/เดือน) + ชำระรายเดือน/รายปี |
| ผังบัญชี/สูตรตั้งต้น | แบบธุรกิจบริการชุดเดียว | template หลายประเภทธุรกิจ (บริการ ซื้อมาขายไป) ให้เลือกตอนสร้างบริษัท |
| สต๊อก/ทรัพย์สิน | นอกขอบเขต | ยังเป็น P2 แต่ data model ต้องรองรับตั้งแต่แรกเพราะลูกค้าซื้อมาขายไปจะถามแน่ |
| ฝั่งซื้อ จ่ายเงิน คู่ค้า CN/DN WHT อายุหนี้ ตั้งค่า | อยู่ใน spec แต่ไม่มีใน Design | ต้องมีหน้าจอครบ 1:1 (หัวข้อ 6) |

สิ่งที่ไม่เปลี่ยน: Posting Engine กลาง (สูตรลงบัญชีเป็นข้อมูล ไม่ hardcode), Dr = Cr ตรวจที่ฐานข้อมูล, ลงบัญชีแล้วห้ามลบ, ล็อกงวด, เงินเป็น NUMERIC(18,2), audit log ทุกการกระทำ, API เดียวกับที่ UI และ MCP ใช้

## 2. สถาปัตยกรรม Multi-tenant

เลือกแบบ **schema-per-company บน Postgres cluster เดียว** และย้ายบริษัทใดก็ได้ออกไปเป็น database แยกโดยโค้ดไม่เปลี่ยน เหตุผล: ระบบบัญชีรับความผิดพลาด "ลืม filter แล้วข้อมูลรั่วข้ามบริษัท" ไม่ได้ และลูกค้าต้องการ backup/restore/ส่งออกข้อมูลทั้งบริษัทเป็นก้อนเดียว

### 2.1 เปรียบเทียบทางเลือก

| ทางเลือก | แยกข้อมูล | ต้นทุนต่อบริษัท | backup/ย้ายทีละบริษัท | งบรวมข้ามบริษัท | ความเสี่ยงรั่ว | เหมาะกับ |
| --- | --- | --- | --- | --- | --- | --- |
| Row-level (`company_id` + RLS) | logical | ต่ำสุด | ยาก (ต้อง filter ทุกตาราง) | ง่าย | สูงสุด (ลืม filter = รั่ว) | B2C ข้อมูลเล็ก |
| **Schema-per-company (เลือก)** | physical ระดับ schema | ต่ำ (connection pool ร่วม) | `pg_dump -n co_xxxx` | query ข้าม schema ได้ | ต่ำ (search\_path ตั้งครั้งเดียวต่อ request) | SaaS หลักพันบริษัท |
| Database-per-company | physical เต็ม | สูง (connection/migration ต่อ db) | ง่ายสุด | ยาก (ต้อง ETL) | ต่ำสุด | ลูกค้า enterprise/on-prem |

ทางเลือกที่ 2 ย้ายไป 3 ได้ด้วย dump schema หนึ่งไปเป็น database ใหม่แล้วชี้ connection string ของบริษัทนั้นไปที่ db ใหม่ ตาราง `public.company` เก็บ `db_dsn` (null = cluster หลัก) ไว้รองรับตั้งแต่แรก

### 2.2 โครงสร้างฐานข้อมูล

| ส่วน | อยู่ที่ | ตาราง | หมายเหตุ |
| --- | --- | --- | --- |
| ตัวตนและสิทธิ์ | `public` | `user`, `tenant`, `company`, `membership` (user × company × role), `invitation`, `api_key` | `tenant` = ลูกค้าที่จ่ายเงิน 1 รายมีหลาย `company` |
| แพ็กเกจและเงิน | `public` | `plan`, `subscription`, `usage_counter`, `invoice_saas` | `usage_counter` นับเอกสาร/เดือนต่อบริษัท |
| งานบัญชีของแต่ละบริษัท | `co_<company_id>` | ทุกตารางจาก spec v1: `account`, `journal`, `journal_line`, `document`, `document_line`, `contact`, `product`, `posting_rule`, `period`, `bank_*`, `tax_*`, `audit_log` | migration ชุดเดียว รันกับทุก schema |
| ข้อมูลอ้างอิงกลาง | `public.ref` | ผังบัญชี template, สูตร template, อัตราภาษี, ปฏิทินภาษี, รหัสธนาคาร | อ่านอย่างเดียวจาก schema บริษัท |

### 2.3 การเลือก schema ต่อ request

1. ทุก request ส่ง JWT ที่มี `user_id` และ header `X-Company-Id`
2. middleware ตรวจว่า `membership(user_id, company_id)` มีอยู่และไม่ถูกระงับ ไม่มี → 403 ก่อนแตะข้อมูลใดๆ
3. ตั้ง `SET LOCAL search_path = co_<id>, public.ref` ใน transaction เดียวกับ query ทั้งหมดของ request นั้น
4. Prisma ใช้ `@@schema` แบบ multiSchema ไม่ได้กับ schema ที่ชื่อเปลี่ยนตามบริษัท จึงใช้ `$executeRaw` ตั้ง search\_path + `$transaction` ครอบทุก request (หรือใช้ Kysely/Drizzle ที่รองรับ dynamic schema ตรงกว่า — ตัดสินใจในหัวข้อ 7)
5. Background job (ค่าเสื่อม recurring แจ้งเตือนภาษี) รับ `company_id` เป็น argument เสมอ ห้ามมี job ที่วนทุกบริษัทโดยไม่ตั้ง search\_path ต่อรอบ

### 2.4 Migration และ provisioning

- `create_company(tenant_id, template)`: สร้าง schema → รัน migration ล่าสุด → copy ผังบัญชี สูตร งวด จาก `public.ref` ตาม template → บันทึก `company.schema_version` ทำใน transaction เดียว ล้มเหลวคือ drop schema
- การ deploy เวอร์ชันใหม่: รัน migration กับทุก schema แบบทีละบริษัท (ไม่ใช่ transaction ใหญ่ก้อนเดียว) เก็บ `schema_version` ต่อบริษัท บริษัทที่ migrate ไม่ผ่านถูกตั้ง `maintenance` และแจ้งเตือน ไม่บล็อกบริษัทอื่น
- ลบบริษัท: soft delete 30 วัน (ปิดการเข้าถึง + dump เก็บใน object storage) จากนั้น `DROP SCHEMA` ตามกฎหมายต้องเก็บเอกสารบัญชี 5 ปี ดังนั้นก่อนลบระบบต้องให้ลูกค้าดาวน์โหลด export ครบชุดก่อน

### 2.5 ขีดจำกัดที่รู้ล่วงหน้า

- Postgres รับ schema หลักพันได้สบาย แต่ catalog จะโตตามจำนวนตาราง × บริษัท (40 ตาราง × 2,000 บริษัท = 80,000 ตาราง) ยังอยู่ในช่วงที่ใช้งานจริงกันทั่วไป เกินหมื่นบริษัทค่อย shard ตาม `tenant_id` ไปหลาย cluster ซึ่ง `company.db_dsn` รองรับอยู่แล้ว
- Connection pool (PgBouncer) ต้องเป็น transaction mode และ search\_path ต้องตั้งด้วย `SET LOCAL` เท่านั้น มิฉะนั้น connection ที่ถูก reuse จะพาสิทธิ์ของบริษัทก่อนหน้าติดมา นี่คือ test ที่ต้องมีตั้งแต่วันแรก

## 2A. One Platform — AccountSystem เป็น hub ของ Innovera

ตัดสิน 6 พ.ย.: AccountSystem กับ TMS (และแอป Innovera อื่นในอนาคต) เป็น**คนละแอป คนละ database คนละ deploy** แต่ AccountSystem เป็นฝ่ายรองรับการเชื่อมต่อ (hub) ที่แอปอื่นมาต่อ เหมือนที่ PEAK/FlowAccount เป็น connector ในหน้า "เชื่อมระบบบัญชี" ของ TMS v4 — AccountSystem ต้องเป็นตัวเลือกหนึ่งในนั้น และเป็นตัวที่เชื่อมได้ลึกที่สุด เพราะเราคุมทั้งสองฝั่ง

"One platform" จึงหมายถึงชั้นบนสุดที่ใช้ร่วมกัน ไม่ใช่โค้ดเดียวกัน:

| ชั้น | ใช้ร่วมกัน | แยกกัน |
| --- | --- | --- |
| Innovera ID | login เดียว (OIDC) ทุกแอปรับ token จากที่เดียวกัน | — |
| ทะเบียนบริษัทและสมาชิก | `tenant`, `company` (เลขผู้เสียภาษีเป็น key), `membership` กลาง | แต่ละแอปเก็บ role และสิทธิ์ของตัวเอง |
| Billing | plan และการชำระกลาง ซื้อหลายแอปในบิลเดียว | quota ต่อแอป |
| Platform console | หน้าเลือกแอป/บริษัท + หน้าเชื่อมแอปเข้าด้วยกัน | — |
| ข้อมูลธุรกิจ (คู่ค้า เอกสาร journal) | — | แยก database ต่อแอป เชื่อมผ่าน API หัวข้อ 5.12 |

### 2A.1 สิ่งที่ AccountSystem ต้องเตรียมในฐานะ hub

| รหัส | ข้อกำหนด | ลำดับ |
| --- | --- | --- |

| FR-HB-02 | หน้า "แอปที่เชื่อมต่อ" ในตั้งค่าบริษัท: แสดง TMS/แอปอื่นที่เชื่อมอยู่ สถานะ เอกสารที่รับเข้ามา 7 วัน รายการผิดพลาด ปุ่มตัดการเชื่อม | P1 |
| FR-HB-03 | One-click connect สำหรับแอป Innovera: TMS กด "เชื่อม AccountSystem" → เด้งมาหน้า consent ของเรา → เลือกบริษัท → ออก API key ผูก scope ให้อัตโนมัติ (OAuth2 authorization code) ไม่ต้อง copy key | P1 |
| FR-HB-04 | การเชื่อมแบบ API key ธรรมดาสำหรับระบบที่ไม่ใช่ของ Innovera ยังมี (FR-ST-07) | P1 |
| FR-HB-05 | คู่ค้า sync สองทางระหว่างแอป ใช้เลขผู้เสียภาษี+สาขาเป็น key จับคู่ ไม่มีเลขผู้เสียภาษี (คนขับ บุคคล) ใช้ external\_ref และให้ผู้ใช้ยืนยันคู่ที่ชื่อคล้าย | P1 |
| FR-HB-06 | เอกสารที่มาจากแอปอื่นแสดง badge แหล่งที่มา + ลิงก์กลับไปเอกสารต้นทาง (deep link) และแก้ได้เฉพาะส่วนบัญชี (สูตร บัญชี มิติ) ไม่ให้แก้ยอด/บรรทัดที่เป็นของแอปต้นทาง | P1 |
| FR-HB-07 | Webhook ขาออกส่งสถานะกลับแอปต้นทาง (ชำระแล้ว ยกเลิก ออก 50 ทวิแล้ว) พร้อม retry + หน้าดู delivery log | P1 |
| FR-HB-08 | SDK/ตัวอย่าง connector (TypeScript) ที่แอป Innovera ตัวอื่นนำไปใช้ได้ทันที (PropSpace, guard-dispatch) | P2 |

### 2A.2 ผลต่อ TMS v4

- เพิ่ม "AccountSystem (Innovera)" เป็น connector แรกในหน้าเชื่อมระบบบัญชี ปุ่ม "เชื่อมต่อ" ของตัวนี้ใช้ one-click (FR-HB-03) ส่วน PEAK/FlowAccount ยังใช้ API key ของเจ้านั้นตามเดิม
- TMS ยังมีทะเบียนลูกค้า/รถร่วมของตัวเอง และหน้าบัญชีของ TMS (วางบิล รับชำระ Settlement เงินเบิก) เป็นหน้า "เตรียมและส่ง" ส่วนการลงบัญชี ภาษี และงบเป็นของ AccountSystem
- สถานะ "รอส่งเข้า PEAK" ใน TMS กลายเป็น "รอส่งเข้า AccountSystem" และเมื่อเราส่ง webhook `payment.received` กลับ DO จะเปลี่ยนเป็น "ชำระแล้ว" โดยไม่ต้องให้คนกดซ้ำ
- หัวข้อ 5.12 (FR-IG-01..10) คือ contract ที่ TMS ใช้จริง ไม่เปลี่ยนแปลง

### 2A.3 สิ่งที่ยังไม่ทำใน v1

- Innovera ID และ Platform console เป็นโครงการแยก ทำหลังจาก AccountSystem และ TMS ใช้งานได้แล้วทั้งคู่ จนกว่าจะมี แต่ละแอป login ของตัวเองและเชื่อมกันด้วย API key (FR-HB-04) ซึ่งใช้ได้จริงตั้งแต่วันแรก

ข้อสังเกตที่เปลี่ยน spec ของเรา:

1. ทุกเจ้าตั้งค่าได้ว่า CN/DN ที่ไม่อ้างอิงเอกสารต้นทางจะลงบัญชีอย่างไร เราใส่เป็นสูตรแยก `CN[no-ref]` ใน posting rule ตั้งต้น
2. PEAK แยก "ใบกำกับภาษี" กับ "ใบแจ้งหนี้" รวมหรือแยกกันได้ตามนโยบายบริษัท (VAT split default) เราต้องมี setting นี้ระดับบริษัท เพราะธุรกิจบริการจำนวนมากออกใบกำกับเมื่อรับเงิน ไม่ใช่เมื่อแจ้งหนี้
3. Odoo ไม่มีรายการปิดปี ใช้วิธีคำนวณกำไรสะสมแบบ real-time เราใช้แนวนี้สำหรับงบ แต่ยังสร้าง journal ปิดปีเมื่อผู้ใช้กด เพื่อให้ตรงกับที่สำนักงานบัญชีไทยคุ้นเคย
4. ลูกค้ากลุ่มสำนักงานบัญชีคือช่องทางขายหลักของทุกเจ้า (partner program) เราทำ plan Firm และ dashboard รวมลูกค้าตั้งแต่ P1

### 5.12 Integration contract สำหรับ TMS (และระบบปฏิบัติการอื่น)

อ้างอิงจาก TMS v4 (Claude Design) ของ Innovera: TMS มีหน้า "เชื่อมระบบบัญชี" เลือก connector ได้ 1 ตัว (ตอนนี้มี Express, FlowAccount, PEAK, KRS, SAP B1) และมี Open API ของตัวเอง (API key + webhook) AccountSystem ต้องเป็น connector ตัวที่ 6 ในรายการนั้น และเป็นตัวเดียวที่ส่งสถานะกลับได้ครบ

เอกสารที่ TMS สร้างและต้องไหลเข้าบัญชี:

| --- | --- | --- | --- |
| วางบิลและใบแจ้งหนี้ (จาก DO ที่ส่งแล้ว) | ลูกค้า, ช่วง DO, บรรทัดค่าขนส่งต่อเที่ยว, บริการประกอบ | BN ใบวางบิล + IV ใบแจ้งหนี้/ใบกำกับ | ค่าขนส่งยกเว้น VAT, บริการประกอบ VAT 7% → ต้องรองรับรหัสภาษีต่างกันในบิลเดียว (FR-SL-03 รองรับแล้ว) |
| รับชำระ | เงินเข้า, อ้างอิงใบแจ้งหนี้, ภาษีถูกหัก | RV ใบเสร็จรับเงิน | ลูกค้าหัก ณ ที่จ่าย 1% ค่าขนส่ง → บรรทัด WHT ฝั่งรับ |
